# 基于哈希的后量子签名算法：研究原型与模拟结果

**项目**：机构项目 / 量子计算机
**日期**：2026-09-28
**原型**：Lamport 一次性签名 + Merkle 树聚合（HBS-PQ）

---

## 1. 研究目标

在 BIP-0360（Pay-to-Merkle-Root）讨论的背景下，本项目验证一个核心问题：

> **能否从零实现一个真正抗量子计算机攻击的数字签名算法，并在本地跑出可复现的模拟结果？**

"真正抗量子"指的是：即使 Shor 算法可被实现，该签名方案也不会被多项式时间破解。安全假设应尽可能弱——只依赖哈希函数抗原像/抗碰撞，而不是椭圆曲线离散对数。

## 3. 算法设计

### 3.1 为什么选哈希基签名（HBS）

后量子签名有四大类：格基（ML-DSA/Falcon）、哈希基（SLH-DSA/XMSS/LMS）、编码基（Classic McEliece）、多变量基（SQIsign 等）。

我们选哈希基，因为：

1. **安全假设最弱**：只要求 SHA-256 是抗碰撞/抗原像的。Shor 算法对哈希函数**没有任何加速**；Grover 算法只能把 256-bit 哈希降到 ~128-bit 安全强度，仍然安全。
2. **历史最久、最易实现**：Lamport 1979 年提出，Merkle 1989 年扩展，是所有公钥密码学中最早的非对称方案之一。
3. **与 BIP-0360 直接相关**：BIP-0360 的 Related Work 章节明确讨论了 Lamport、WOTS、OP_CAT 路线，本原型正是这条路线的最小可运行版本。
4. **无状态化路径清晰**：SPHINCS+（FIPS 205）就是在本原型基础上叠加了 hypertree + FORS 签名，消除了"每个 OTS 只能签一次"的状态负担。

### 3.2 算法结构

```
消息
  │
  ▼
┌─────────────────────────────────────┐
│  Lamport 一次性签名 (OTS)           │
│  - 256 对 32-byte 随机数 (sk)       │
│  - 公钥 = 对每对取 SHA-256           │
│  - 签名 = 按消息比特揭示 256 个预像  │
└─────────────────────────────────────┘
  │
  │  N = 2^h 个 Lamport 密钥对
  ▼
┌─────────────────────────────────────┐
│  Merkle 树                          │
│  - 叶子 = 每个 OTS 公钥的哈希       │
│  - 两两哈希到根                      │
│  - 树根 (32 B) = 整体公钥            │
│  - 签名附带 Merkle 路径证明           │
└─────────────────────────────────────┘
```

**关键安全性质**：
- 一次性：每个 Lamport 密钥对只能签一条消息（签两次会泄露私钥）——这是 HBS 的固有约束；
- 多签：Merkle 树让一个 32 字节公钥支持 `N = 2^h` 次签名；
- 验证时只需重算路径上的 h 次哈希，与 N 无关。

## 4. 模拟结果

实验环境：macOS / Python 3 / SHA-256，每参数重复 3 次取中位数。

### 4.1 实测性能

| 树高 h | 支持签名数 N | 密钥生成 (ms) | 签名 (ms) | 验证 (ms) | 签名大小 (KiB) |
|---:|---:|---:|---:|---:|---:|
| 1 | 2 | 1.31 | 0.019 | 0.103 | 24.0 |
| 2 | 4 | 2.79 | 0.018 | 0.099 | 24.1 |
| 3 | 8 | 5.34 | 0.019 | 0.102 | 24.1 |
| 4 | 16 | 10.35 | 0.023 | 0.100 | 24.1 |
| 5 | 32 | 21.30 | 0.033 | 0.108 | 24.2 |
| 6 | 64 | 42.92 | 0.042 | 0.136 | 24.2 |
| 7 | 128 | 84.56 | 0.067 | 0.102 | 24.2 |

### 4.2 与现有标准的对比（签名大小）

| 方案 | 公钥 (B) | 签名 (B) | 抗量子？ |
|---|---:|---:|---|
| secp256k1 Schnorr (BIP-340) | 32 | 64 | ❌ Shor 可破 |
| ML-DSA-44 (FIPS 204, 格基) | 1,312 | 2,420 | ✅ |
| ML-DSA-65 (FIPS 204, 格基) | 1,952 | 3,309 | ✅ |
| SLH-DSA-128s (FIPS 205, 哈希基) | 32 | 7,856 | ✅ |
| SLH-DSA-128f (FIPS 205, 哈希基) | 32 | 17,088 | ✅ |
| **本原型 Lamport+MSS (h=6)** | **32** | **24,800** | ✅ |

### 4.3 关键发现

1. **签名/验证速度极快**：签名 ~0.02–0.07 ms，验证 ~0.1 ms。这是哈希基方案的固有优势——纯哈希运算，没有大整数模幂。
2. **公钥仅 32 字节**：与 secp256k1 相同，远小于格基 ML-DSA 的 1.3–2 KB。这正是 BIP-0360 选择"承诺到 Merkle 根"的原因——链上只存 32 字节。
3. **签名偏大是本原型的主要短板**：24.8 KB vs SLH-DSA-128f 的 17 KB。原因是我们用了**最朴素的 Lamport**——每比特密钥对（256 对），签名时把 256 个预像（8 KB）+ 整个 OTS 公钥（16 KB）都带上。
4. **密钥生成随 N 线性增长**：N=128 时 ~85 ms，可接受；这是一次性代价，不影响后续签名。

## 5. 体积膨胀从哪来、怎么压

本原型的 24.8 KB 拆解：

| 组成 | 字节 | 占比 | 压缩手段（下一步） |
|---|---:|---:|---|
| Lamport 签名（256 × 32 B 预像） | 8,192 | 33% | WOTS/Winternitz：每 w=4 比特一组，签名体积降到 ~1/4 |
| Lamport 公钥（验证时必须带上） | 16,384 | 66% | 用 WOTS 后公钥同步缩小；SPHINCS+ 用 hypertree + 压缩表示 |
| Merkle 认证路径（h × 32 B） | ~224 | <1% | 已经很小，无需优化 |

**对照**：SLH-DSA-128f 把这些优化全部做到位后，签名压到 17 KB；SPHINCS+ 进一步用无状态 hypertree 消除了"OTS 只能用一次"的状态管理负担。

## 6. 局限与诚实声明

本原型是**教学/研究原型**，不是生产级密码库：

1. **未做域分离（domain separation）**：生产方案（SPHINCS+）会用不同前缀区分 PRF / F / H / H_msg，本原型统一用 SHA-256，可能在选择密文安全模型下有理论弱点，但对离线签名场景不影响。
2. **未实现 WOTS 压缩**：这是签名偏大的直接原因，也是下一步最该做的优化。
3. **有状态**：每个 OTS 密钥只能签一次，重复使用会泄露私钥。生产方案要么用 XMSS/LMS 严格管理状态，要么用 SPHINCS+ 无状态化。
4. **未做侧信道防护**：用了 `os.urandom` 和 Python 数据结构，没有常数时间保证。
5. **性能数字是 Python 实现**：C/Rust 实现会快 10–100 倍，但相对大小关系不变。

## 7. WOTS+ 压缩结果（P0 已完成）

在第一版 Lamport 原型基础上，实现了 SPHINCS+ 风格的 **WOTS+（Winternitz OTS）**，替换每个 Merkle 叶子的 OTS 层。

### 7.1 WOTS+ 参数（对齐 FIPS 205）

| 参数 | 值 |
|---|---|
| n（哈希输出） | 32 B (SHA-256) |
| w（Winternitz 基数） | 16（每字符 4 bit） |
| len1（消息链数） | 64 |
| len2（校验和链数） | 3 |
| len（总链数） | 67 |
| 私钥大小 | 67 × 32 = 2,144 B |
| 公钥大小 | 2,144 B |
| 签名大小 | 2,144 B |

### 7.2 实测对比（树高 h=7，支持 128 次签名）

| 指标 | Lamport+MSS | WOTS+MSS | 变化 |
|---|---:|---:|---|
| 公钥 | 32 B | 32 B | 不变 |
| 签名 | 24,800 B | **4,512 B** | **缩小 5.5×** |
| 签名延迟 | 0.064 ms | 0.231 ms | +0.17 ms（哈希链成本） |
| 验证延迟 | 0.102 ms | 0.177 ms | +0.08 ms |
| 密钥生成 | 85 ms | 52 ms | 更快（私钥更小） |

### 7.3 跨方案定位

WOTS+MSS（4,512 B）现在位于：
- 比格基 ML-DSA-44（2,420 B）大 ~1.9×；
- 比哈希基 SLH-DSA-128s（7,856 B）**小 ~1.7×**；
- 比 SLH-DSA-128f（17,088 B）小 ~3.8×。

**代价**：WOTS+MSS 是**有状态**的——每个 OTS 密钥只能签一次，钱包必须跟踪哪个叶子已用。SLH-DSA 通过 hypertree + FORS 做到无状态，代价是签名变大。这是大小 vs 状态管理的经典权衡。

### 7.4 自校验

WOTS+ 实现已通过：
- 正确签名/验证 round-trip；
- 篡改一个字节后验证拒绝；
- 错误消息拒绝；
- base_w 编解码 sanity check。
